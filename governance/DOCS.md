# Документооборот Fonotext — правила хранения документации

> Действует для обоих контуров проекта: публичного (этот репозиторий) и закрытого.
> Для агентов обязателен вместе с `AGENTS.md`. Проверяется машинно:
> `python3 tools/docs-registry.py --check` (CI) и ежемесячной задачей `docs-review`.

## 0. Какую проблему это решает

Документы появляются быстрее, чем кто-либо успевает помнить, где правда. Через месяц
в репозитории живут три версии одного текста, два отчёта с противоположными выводами
и страница, которую сняли с публикации, но она всё ещё открывается. Читатель — человек
или агент — не может отличить актуальное от исторического, поэтому либо переспрашивает,
либо действует по устаревшему.

Правила ниже держат три вещи: **одно место правды для каждого типа документа**,
**видимый статус актуальности** и **регулярную ревизию**, которая не даёт мёртвому
грузу накапливаться.

## 1. Карта: что где живёт

Два репозитория и одна доска. Документ живёт ровно в одном месте; остальные ссылаются.

| Что | Где | Источник истины для |
|---|---|---|
| Публичные страницы сайта (`docs/*.md`) | этот репозиторий | описания продукта, архитектуры, API, безопасности |
| Спецификации функций (`docs/10-feature-specs/`) | этот репозиторий | что именно делает функция и как её принимают |
| Правила, реестры, шаблоны (`governance/`) | этот репозиторий | как мы работаем |
| Ресёрч, аудит, выводы (`artifacts/`) | этот репозиторий — только публично-безопасное | доказательная база публичных решений |
| Стратегия, экономика, канон цифр, внутренние ресёрчи | закрытый контур | решения и цифры |
| Журнал технических решений | закрытый контур | почему сделано именно так |
| Задачи, статусы, приоритеты | GitHub Issues + Projects | что делается и кем |
| История изменений | git | кто, когда и что поменял |

Правило одного источника: если один и тот же текст нужен в двух местах — он живёт
в одном, второе место на него **ссылается**. Копия считается ошибкой, а не удобством.

### Почему артефакты не в публичном репозитории по умолчанию

Публичный контур проходит лексический чекер границ (`AGENTS.md` §2). Ресёрч почти всегда
содержит то, что в публичный контур нельзя: условия поставщиков, имена заказчиков,
сравнения. Поэтому **по умолчанию артефакт идёт в закрытый контур**, а в публичный —
только если после проверки в нём не осталось ничего внутреннего. Решение принимает
чекер, а не автор артефакта.

## 2. Типы документов

Тип определяет место, владельца и срок ревизии. Тип указывается в реестре
(`governance/docs.yml`) или в шапке артефакта.

| Тип | Что это | Где | Владелец | Ревизия |
|---|---|---|---|---|
| `landing` | точка входа: README, карта проекта | корень | product | 90 дней |
| `page` | публичная страница сайта | `docs/` | product / tech | 180 дней |
| `spec` | спецификация функции | `docs/10-feature-specs/` | product | 180 дней |
| `policy` | правила, регламенты, этот документ | `governance/` | governance | 180 дней |
| `recurring` | регулярная проверка с чек-листом | `governance/recurring/` | governance | 180 дней |
| `template` | шаблон заявки, отчёта, артефакта | `governance/templates/` | governance | 365 дней |
| `guide` | инструкция по инструменту или стенду | рядом с инструментом | tech | 180 дней |
| `legal` | лицензия, правовые тексты | корень | governance | 730 дней |
| `tombstone` | снятая с публикации страница: заглушка с `noindex` | `docs/` | product | не ревизуется |
| `artifact` | ресёрч, аудит, отчёт, выводы | `artifacts/` или закрытый контур | автор | 180 дней |

Документ без владельца не считается документом: `owner` — обязательное поле. Владелец
не «пишет всегда сам», он отвечает за то, что документ не врёт.

## 3. Жизненный цикл

```
draft ──► active ──► deprecated ──► archived
             ▲            │
             └── обновление (новая версия вместо старой)
```

| Статус | Значит | Что обязано быть |
|---|---|---|
| `draft` | в работе, на него нельзя ссылаться как на норму | владелец, срок |
| `active` | действует, на него можно опираться | владелец, дата ревизии |
| `deprecated` | устарел, но нужен для истории | `superseded_by` + видимый баннер |
| `archived` | исторический, не действует | `superseded_by` или явная причина |
| `tombstone` | снято с публикации | заглушка с `noindex` и редиректом |

Три запрета, которые проверяет CI:

1. **Нельзя удалить документ, на который есть ссылки.** Сначала `deprecated` + замена,
   через ревизию — `archived`.
2. **Нельзя оставить `deprecated` без замены.** Читатель должен попасть в актуальное.
3. **Нельзя держать документ со статусом «действует», если он врёт.** Есть сомнение —
   переводи в `draft` и ставь задачу, а не оставляй «как есть».

### Как устаревает документ

Признаки, по которым документ пора ревизовать (по ним же работает ежемесячная задача):

- истёк срок ревизии (считается от даты последней правки в git);
- текст описывает то, чего в продукте уже нет (проверяется сверкой со спецификациями);
- появился документ-заменитель, а старый остался `active`;
- артефакт старше 120 дней: выводы могли не пережить изменения продукта;
- на документ нет входящих ссылок и он не входит в индекс — кандидат в `archived`.

## 4. Артефакты: ресёрч, аудит, выводы

**Правило владельца:** артефакт живёт в GitHub. Отчёт, который лежит только на диске,
не существует: его не найдут ни агенты, ни человек через месяц, а ссылки из задач
и документов превратятся в пустоту.

### Как заводится артефакт

```bash
python3 tools/docs-registry.py --new research "рынок-речевой-аналитики"
```

Команда создаёт файл `artifacts/research/ГГГГ-ММ-ДД-рынок-речевой-аналитики.md`
с готовой шапкой и структурой. Дальше — заполнить разделы и закоммитить.

### Шапка артефакта

Первая строка файла, до заголовка. В отрендеренном виде не видна, читается скриптами:

```markdown
<!-- artifact
type: research
date: 2026-11-02
status: active
owner: research
contour: public
review_after: 2027-05-01
sources: docs/02-architecture.md
-->
```

Обязательные поля: `type`, `date`, `status`, `owner`, `contour`. `review_after` и `sources`
заполняются всегда, когда применимы. Полный шаблон — `governance/templates/ARTIFACT.md`.

### Куда класть

| Контур | Куда | Что можно |
|---|---|---|
| Публичный | `artifacts/research/`, `artifacts/audit/`, `artifacts/reports/` | только прошедшее чекер границ |
| Закрытый | зоны артефактов закрытого контура | всё внутреннее |

Проверка перед коммитом в публичный контур:

```bash
python3 tools/check-boundaries.py docs README.md artifacts --profile public
```

Нарушение = артефакт уходит в закрытый контур, а не «переформулируется до прохождения».

### Почему шапка, а не реестр

Реестр годится для документов, которые правятся редко и проходят ревью: их немного,
и запись в реестре — часть правки. Артефактов много, их пишут на ходу, и они должны
оставаться самодостаточными: файл, вынутый из репозитория, обязан сам сообщать, когда
он написан и чей он. Поэтому метаданные живут в файле, а индекс собирается из них.

## 5. Устаревание: как это выглядит для читателя

1. **Шапка/реестр** — машинный статус (`status: superseded`, `superseded_by`).
2. **Баннер в первой строке после заголовка** — для человека:

```markdown
> ⚠️ **Устарело** (2026-12-01). Замена: `artifacts/research/2027-01-20-новый-разбор.md`.
```

3. **Индекс** — раздел «Устарело и заменено» со ссылкой на замену.

Перевод в устаревшие — командой, чтобы не забыть ни один из трёх шагов:

```bash
python3 tools/docs-registry.py --deprecate artifacts/research/2026-11-02-имя.md \
    --by artifacts/research/2027-01-20-новый-разбор.md
python3 tools/docs-registry.py --deprecate docs/02-architecture.md --by docs/03-models.md
```

## 6. Чистота папок

«Чисто» — это проверяемое состояние, а не ощущение. Для каждой зоны:

| Зона | Чисто, когда |
|---|---|
| корень | только `README`, `AGENTS`, `CLAUDE`, `LICENSE`, `AGENTS`-инфраструктура; никаких отчётов и черновиков |
| `docs/` | только публикуемое; каждая `.md` собрана в `.html` или помечена `build: none`; нет страниц без источника и записи в реестре |
| `governance/` | правила, реестр, шаблоны, регулярные задачи; ни одного отчёта |
| `artifacts/` | только артефакты с шапкой; устаревшие помечены, а не удалены |
| `tools/` | только исполняемые инструменты и их конфиги; выходные файлы — в `.gitignore` |

Автопроверки: незарегистрированный документ, документ вне git, битая относительная
ссылка, страница без источника, дубли по заголовку, просроченная ревизия.

## 7. Регулярная ревизия

| Ритм | Что | Кто |
|---|---|---|
| на каждом коммите | `docs-registry.py --check`, чекер границ, аудит сайта | автор правки |
| раз в месяц | задача `docs-review`: обход индекса, разбор предупреждений, назначение замен | агент-аудитор |
| раз в квартал | пересмотр сроков ревизии и типов; удаление архивного мусора | координатор |
| при релизе | сверка спецификаций и страниц с фактическим состоянием продукта | product + tech |

Ежемесячная задача создаётся автоматически (`.github/workflows/docs-review.yml`,
1-е число) и живёт в Issues с меткой `docs-review`; чек-лист — в
`governance/recurring/docs-review.md`. Задача — не формальность: каждый её пункт
закрывается либо правкой, либо новой задачей.

## 8. Инструменты

| Команда | Что делает |
|---|---|
| `python3 tools/docs-registry.py --check` | проверка реестра, шапок, ссылок, старения |
| `python3 tools/docs-registry.py --check --strict` | то же, но просроченная ревизия = нарушение |
| `python3 tools/docs-registry.py --index` | пересобрать `governance/DOCS-INDEX.md` |
| `python3 tools/docs-registry.py --check-index` | индекс не разъехался с реестром (CI) |
| `python3 tools/docs-registry.py --new <type> "<slug>"` | создать артефакт с шапкой |
| `python3 tools/docs-registry.py --deprecate <path> --by <path>` | перевести в устаревшие |
| `python3 tools/check-boundaries.py docs README.md [artifacts] --profile public` | границы публичного контура |
| `python3 tools/site-audit.py` | технический аудит сайта |

## 9. Как начать новую работу

| Ситуация | Что делать |
|---|---|
| Новая публичная страница | создать `docs/NN-slug.md` → добавить в `PUBLISH` в `tools/build-docs-html.py` → запись в реестр → собрать html |
| Новый ресёрч или аудит | `docs-registry.py --new research "<slug>"` → заполнить → прогнать чекер границ → выбрать контур → закоммитить |
| Новое правило или регламент | файл в `governance/` → запись в реестр с типом `policy` |
| Документ устарел | `--deprecate` с заменой → проверить входящие ссылки → `--index` |
| Нашёл расхождение или утечку | **новая задача**, не править «заодно» (AGENTS.md §4) |
| Нужна цифра, которой нет в каноне | заявка `governance/templates/REQUEST.md`, задача → `ЖДЁТ РЕШЕНИЯ` |

## 10. Что проверяет CI

1. Каждый документ из управляемых зон зарегистрирован в `governance/docs.yml`.
2. Каждая запись реестра указывает на существующий файл.
3. У артефактов есть корректная шапка; у устаревших — замена и баннер.
4. Относительные ссылки в правилах и артефактах разрешаются.
5. Индекс соответствует реестру.
6. Документ на диске, но не в git — предупреждение, а не блокировка.

Блокируют только нарушения. Предупреждения (просроченная ревизия, старый артефакт,
дубль) разбираются в ежемесячной задаче — иначе они превратятся в фон, который
перестают читать.

## 11. Частые ошибки

| Ошибка | Почему плохо | Как правильно |
|---|---|---|
| «Скопирую текст в реестр, чтобы было видно» | две правды расходятся за неделю | ссылка на источник |
| «Удалю устаревшее, зачем мусор» | ломаются ссылки и история решений | `deprecated` + замена |
| «Отчёт приложу в задачу файлом» | файл в issue не ищется и не индексируется | артефакт в репозитории, в задаче — ссылка |
| «Дата правки в реестре» | реестр расходится с git | дата берётся из git |
| «Один большой документ про всё» | ревизия невозможна: непонятно, что устарело | один документ — одна тема |
| «Пока черновик, в реестр не внесу» | черновик теряется | `status: draft` — это тоже регистрация |
